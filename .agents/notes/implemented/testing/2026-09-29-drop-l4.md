# Agent Note: Drop automated provider-drift monitoring (L4)

Status: implemented

## Problem

When ChatGPT, Claude, Grok, Copilot, Antigravity, or Cursor change their
login or API surface, the plugin breaks on *every* DSH version at once —
outside everything the DSH version matrix can catch. The virtual-provider
tests (L3) cannot catch it either: a fake replays the contract as recorded,
so the suite stays green while production breaks. Provider-side drift
needs a backstop that observes the real providers — but the standing
project principle is that **automated tests never touch production
provider servers** (see the credentials policy in `docs/testing.md`).

## Decision

No automated provider monitoring. The backstop is a **manual pre-release
canary**: before tagging a release, log in once per provider in an isolated
profile and run one model request — the "use it to know" step. Canary
status is recorded per provider in the README migration notes. If the
canary fails, check the provider's status page first — but status pages
only reflect declared incidents; they are not polled and never substitute
for the login itself.

This is the third iteration, and the history matters because each stage
taught something about what "monitoring" can actually observe:

1. **Junk-grant probing (built, then removed).** The first version POSTed
   invalid grants to providers' token/authorize/device endpoints and
   classified the error responses. Removed: POSTing bad credentials to
   someone else's token endpoint is indistinguishable from
   credential-stuffing to their abuse systems. Not worth antagonizing
   providers for a signal.
2. **Metadata-only monitoring (kept briefly, then dropped).** Tier 1 hard
   signals (`exit 1` on drift) compared the OIDC discovery documents of
   Codex, Google, and Grok — `issuer`, `authorization_endpoint`,
   `token_endpoint`, plus a whole-document hash — against
   `provider-metadata.baseline.json`; Tier 2 soft signals (report-only)
   hashed the OpenAI/Anthropic/GitHub/Cursor changelog pages. It never
   touched token/authorize/device/models/API endpoints. `--update-baseline`
   refreshed the baseline, with git history as the drift log, and the
   baseline's `_notes` captured real quirks: the Codex plugin hardcodes
   `/oauth/authorize` while discovery advertises `/api/accounts/authorize`;
   Grok pulls discovery at runtime during login; Google's discovery matches
   the `antigravity.ts` constants exactly.

Stage 2 was dropped because a green metadata check would have certified
the wrong thing. Discovery documents don't cover the endpoints that
actually break — claude.ai OAuth, github.com OAuth, and Cursor's
`api2.cursor.sh` publish no usable metadata — and the drift that breaks
logins is behavioral (flow changes, token semantics, claim shapes), not
metadata. The upkeep (baseline refreshes, changelog-hash triage) bought
coverage of the provider surfaces least likely to fail, while the surfaces
most likely to fail had no metadata to watch.

## Alternatives considered

- **Keep the metadata monitor.** Rejected: upkeep cost against a signal
  that structurally misses the failure class. A monitor that can't see
  claude.ai, github.com OAuth, or `api2.cursor.sh` is a dashboard, not a
  backstop.
- **Restore endpoint probing with gentler requests** (e.g. GETs against
  authorize URLs). Still touches production on a schedule from CI
  infrastructure, still needs no user in the loop, and still answers a
  narrower question than "can a user log in." Rejected on the same
  principle.
- **Real-API e2e in CI, à la deepseek-harness.** The harness runs its
  keyless gate plus a secret-bearing real-API workflow against its own
  API. Our position is different: we integrate six third-party consumer
  OAuth flows, and CI holds no credentials for any of them. Building a
  secret-bearing CI lane would mean storing six sets of personal
  credentials in automation and hitting production on every run — exactly
  what the project principle forbids.
- **More fakes.** Cannot help by construction: a fake can only replay the
  contract as recorded. New fakes would test new guesses, not new reality.

## Consequences

Provider drift has no automated coverage, deliberately. Releases depend on
maintainer discipline to run the canary before tagging — the one part of
the system that runs on honor. The upside is honesty: nothing in CI
pretends to watch the providers, so a silent provider change can't hide
behind a green badge. If the canary ever becomes too burdensome to run per
release, that is the signal to revisit — not to quietly re-add a monitor
that watches the wrong surfaces.
