# Agent Note: Drop automated provider-drift monitoring (L4)

Status: implemented

## Problem

When ChatGPT, Claude, Grok, Copilot, Antigravity, or Cursor change their
login or API surface, the plugin breaks on *every* DSH version at once —
outside everything the DSH version matrix can catch. The virtual-provider
tests (L3) cannot catch it either: a fake replays what was recorded, so the
suite stays green while production breaks. Provider-side drift needs a
backstop that observes the real providers.

## Decision

No automated provider monitoring. The backstop is a **manual pre-release
canary**: before tagging a release, log in once per provider in an isolated
profile and run one model request — the "use it to know" step. Provider
canary status is recorded per provider in the README migration notes.
Automated tests never touch production provider servers, by design.

## Alternatives considered

- **Probing token/authorize/device endpoints with junk grants.** Built
  first, then removed: POSTing invalid grants to someone else's token
  endpoint is indistinguishable from credential-stuffing to their abuse
  systems. Rejected — not worth antagonizing providers for a signal.
- **Metadata-only monitoring** (hashing OIDC discovery documents and
  changelog pages against a baseline). Kept briefly, then dropped: the
  upkeep wasn't worth it next to the canary, and discovery documents don't
  cover the endpoints that actually break — claude.ai OAuth, github.com
  OAuth, and Cursor's `api2.cursor.sh` publish no usable metadata. A green
  metadata check would have certified the wrong thing.
- **More fakes.** Cannot help by construction: a fake can only replay the
  contract as recorded. New fakes would test new guesses, not new reality.

## Consequences

Provider drift has no automated coverage, deliberately. Releases depend on
maintainer discipline to run the canary before tagging. The upside is
honesty: nothing in CI pretends to watch the providers, so a silent
provider change can't hide behind a green badge.
